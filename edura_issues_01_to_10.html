The 5 Repositories & What Lives in Each
edura-infra
Docker Compose, Nginx config, Kubernetes manifests, CI/CD pipeline YAML, RabbitMQ setup scripts, environment configs
edura-backend
All 11 FastAPI microservices — one folder per service. ORM models, Alembic migrations, routers, business logic, unit tests per service
edura-frontend
Next.js 14 App Router, Redux Toolkit, all page components, UI features per the Figma prototype
edura-tests
Cross-service integration tests, end-to-end smoke tests, load testing scripts that span multiple services
edura-documents
SRS, SDS, ADRs, retrospectives, meeting notes, final development report chapters
The one rule to decide where an issue goes: an issue belongs to the repository whose code it changes. If the work only touches docker-compose.yml, nginx.conf, or .github/workflows/ → edura-infra. If it changes a FastAPI service, ORM model, or Alembic migration → edura-backend. If it changes a Next.js page or Redux slice → edura-frontend. If it only adds integration/E2E test scripts that call multiple services → edura-tests. Documentation or retrospectives only → edura-documents. When work spans two repos (e.g. a feature needs a backend API endpoint AND a frontend page), create one issue in each repo and cross-link them with "Related to #NN in edura-backend".

## User Story As a developer, I want all RabbitMQ exchanges and queues declared idempotently on startup so that any service can publish or consume events immediately without manual broker configuration. ## Background / Context - SDS Reference: Section 2.1 (Message Broker — RabbitMQ), Section 2.3.3 (Why RabbitMQ) - SRS Reference: FR-007 (payment callbacks), FR-009 (automatic course access on payment) The SDS specifies RabbitMQ as the message broker for asynchronous inter-service communication. All events flow through a single topic exchange named edura.events. Publishers use routing keys like payment.success; consumers bind queues to routing key patterns. ## User Story As any system user (Student, Teacher, or Administrator), I want to log in securely with my email and password and receive a JWT access token so that I can access role-appropriate resources without re-authenticating on every request. ## Background / Context - SRS Reference: FR-001 (role-based auth), FR-002 (OTP email verification), NFR-006 (bcrypt), NFR-007 (OTP 5-min expiry) - SDS Reference: Section 7.2 (Authentication Mechanism), Section 7.2.1 (Asgardeo Integration), Section 7.2.2 (Token Management), Section 7.2.3 (Session Management), Section 7.2.4 (OTP), Figure 29 (Authentication Flow), Figure 30 (Registration Flow) - ADR Reference: ADR-07 (JWT over server-side sessions) The SDS specifies Asgardeo as the Identity Provider using OAuth 2.0 PKCE flow. Access tokens are RS256-signed JWTs with 15-minute expiry; refresh tokens expire in 7 days and rotate on each use. OTPs are 6-digit codes stored in Redis with 5-minute TTL. The shared require_role decorator (from issue #04) is finalised here and consumed by all other services. All auth code lives in edura-backend/auth_service/. ## Acceptance Criteria ### AC1: Successful Login Returns Tokens **Given** a registered user with role STUDENT sends POST /api/auth/login with valid email and password **When** Asgardeo validates the credentials via the PKCE flow **Then** the server returns HTTP 200 with {"access_token": "...", "token_type": "Bearer", "expires_in": 900} and sets an HttpOnly Secure cookie containing the refresh token ### AC2: Invalid Credentials Return 401 **Given** a user sends POST /api/auth/login with an incorrect password **When** the server processes the request **Then** the server returns HTTP 401 with body {"error": "INVALID_CREDENTIALS", "message": "Email or password is incorrect"} — no information about which field was wrong ### AC3: JWT Middleware Blocks Unauthorised Requests **Given** a request arrives at any protected endpoint without an Authorization header **When** the require_role middleware processes the request **Then** the server returns HTTP 401 with {"error": "MISSING_TOKEN"}; if the token is present but expired, it returns HTTP 401 with {"error": "TOKEN_EXPIRED"} ### AC4: RBAC Blocks Wrong Role **Given** a STUDENT user sends a request to an endpoint decorated with @require_role(["TEACHER", "ADMIN"]) **When** the middleware validates the role claim in the JWT **Then** the server returns HTTP 403 with {"error": "INSUFFICIENT_PERMISSIONS"} ### AC5: OTP Expires After 5 Minutes **Given** a user requests an OTP via POST /api/auth/otp/request **When** more than 5 minutes pass and the user sends POST /api/auth/otp/verify with the OTP **Then** the server returns HTTP 400 with {"error": "OTP_EXPIRED"} and the OTP is deleted from Redis ### AC6: Refresh Token Rotates on Use **Given** a user holds a valid refresh token and sends POST /api/auth/refresh **When** the server processes the request **Then** a new access token and a new refresh token are returned, and the old refresh token is immediately invalidated in Redis — reusing the old token returns HTTP 401 with {"error": "REFRESH_TOKEN_REUSE"} ## Technical Notes - Asgardeo PKCE: ASGARDEO_CLIENT_ID, ASGARDEO_CLIENT_SECRET, ASGARDEO_TENANT_URL stored in AKS Secrets / GitHub Secrets - JWT validation: use python-jose to verify RS256 signature against Asgardeo's JWKS endpoint (cache the public keys in Redis with 1-hour TTL) - OTP: generate using secrets.randbelow(1000000), zero-pad to 6 digits, store in Redis with key otp:{user_id} and TTL of 300 seconds - Session store: Redis key session:{user_id}:{session_id} → {"role": "STUDENT", "issued_at": "..."} - Maximum 3 concurrent sessions per user (NFR from SDS §7.2.3); on 4th login, invalidate the oldest session - The shared/auth.py require_role decorator must work as both a FastAPI Depends() dependency and a standalone decorator ## Test Requirements - [ ] Unit test: TokenService.create_access_token() — correct claims, correct expiry - [ ] Unit test: TokenService.verify_access_token() — valid token, expired token, tampered signature - [ ] Unit test: OtpService.generate_otp() — 6 digits, stored in Redis with 300s TTL - [ ] Unit test: OtpService.verify_otp() — correct OTP, wrong OTP, expired OTP - [ ] Unit test: require_role decorator — blocks wrong role, passes correct role - [ ] Integration test: POST /api/auth/login with valid credentials → 200 + tokens - [ ] Integration test: POST /api/auth/login with invalid credentials → 401 - [ ] Integration test: POST /api/auth/refresh with valid refresh token → new tokens, old token invalidated - [ ] Integration test: POST /api/auth/refresh with reused refresh token → 401 REFRESH_TOKEN_REUSE ## Definition of Done - [ ] All auth endpoints implemented in edura-backend/auth_service/ - [ ] shared/auth.py require_role decorator finalised and importable by all other services - [ ] Code coverage on auth_service ≥ 90% - [ ] No Asgardeo secrets hardcoded — all read from environment variables - [ ] All unit and integration tests passing in CI - [ ] API docs (/docs) updated with all auth endpoint schemas - [ ] PR raised against develop;
